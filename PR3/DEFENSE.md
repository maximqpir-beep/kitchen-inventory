# Подготовка к защите ПР3

Группа ЭФБО-12-24. Тема: система учета кухонного инвентаря.

## Отладка в IDE
1. Выбери интерпретатор Python и открой main.py.
2. Поставь точку останова на return self.quantity * self.unit_price в models/item.py.
3. Запусти Debug и выбери пункт 1. При расчете первой партии проверь количество 1, цену 125050 и результат 125050 коп.
4. Выполни шаг, затем продолжи выполнение. Для партии из 3 кастрюль стоимость должна составить 375150 коп.
5. Для упражнения временно замени умножение на сложение, найди неправильный результат пошагово, верни умножение и повтори тесты.

## Переход от ПР2 к ПР3
| Данные ПР2 | Класс ПР3 | Атрибуты и поведение |
|---|---|---|
| Словарь предмета | Item | ID, название, ссылки на категорию/состояние/помещение, количество, цена; move_to, change_condition, total |
| ID категории | Category | ID, название, __str__ |
| ID состояния | Condition | ID, название, usable, usage_status |
| ID помещения | Room | ID, название, __str__ |
| Словарь перемещения | Movement | Предмет, исходное и целевое помещение, дата, cancelled, cancel |
| Предмет режущей категории | CuttingItem | Наследует Item, переопределяет handling_note |

## Контрольные вопросы

1. **Класс.** Описание данных и поведения объектов. Item определяет устройство партии инвентаря.

2. **Объект.** Конкретное значение в памяти с типом и состоянием; например, партия ножей.

3. **Класс и объект.** Item — класс, Item(...) — создание его экземпляра. По одному описанию можно создать много объектов.

4. **Экземпляр класса.** Объект, созданный на основе класса; instance и экземпляр обозначают одно понятие.

5. **__init__.** Инициализирует уже созданный экземпляр, записывает исходные атрибуты и проверяет данные. В Item он вызывает check_item.

6. **self.** Обычное имя первого параметра метода экземпляра; Python передает туда текущий объект.

7. **Атрибут класса и объекта.** Атрибут класса принадлежит классу и доступен экземплярам; атрибут экземпляра хранит его собственное значение. self.name относится к конкретному предмету. Общие справочники проекта вынесены в catalog.py.

8. **Метод объекта.** Функция в классе, работающая с экземпляром через self. Например, item.move_to(room).

9. **Метод и функция.** При вызове обычного метода через экземпляр self подставляется автоматически. Обычная функция получает все аргументы явно.

10. **Когда нужен метод.** Когда операция относится к состоянию конкретного объекта: перемещение Item или отмена Movement. Поиск среди многих предметов оставлен функцией.

11. **__str__.** Возвращает понятную пользователю строку. Item.__str__ выводит номер, название, категорию, состояние, помещение, количество и стоимость.

12. **print(object).** Получает строковое представление объекта, обычно через __str__, и выводит его. __str__ обязан вернуть str.

13. **Конструктор.** Создание экземпляра происходит через __new__, после него обычно вызывается __init__ для инициализации. В учебных описаниях __init__ часто называют конструктором, но точнее это инициализатор.

14. **Несколько объектов одного класса.** Да. Восемь начальных партий — отдельные объекты; изменение одного не должно менять другой.

15. **Разные значения атрибутов.** Да. Название, количество, цена, помещение и состояние принадлежат конкретной партии.

16. **Инкапсуляция.** Объединение данных и поведения с контролируемым доступом к состоянию через публичный интерфейс.

17. **Инкапсуляция в проекте.** Item хранит _room, _condition, _quantity; свойства предоставляют чтение, методы проверяют изменения. Подчеркивание — соглашение, не абсолютная защита от доступа.

18. **Наследование.** Определение класса на основе другого с использованием и расширением его поведения. CuttingItem наследует Item.

19. **Отношение «является».** Режущий инвентарь является кухонным инвентарем, поэтому CuttingItem можно использовать там, где ожидается Item.

20. **Почему не наследовать без основания.** Наследование связывает типы и обещает совместимость поведения. Если объект лишь содержит другой объект, лучше использовать связь через атрибут.

21. **Полиморфизм.** Один интерфейс дает поведение соответствующего типа. handling_note вызывается одинаково у Item и CuttingItem, но возвращает разные инструкции.

22. **__str__ и полиморфизм.** str() и print() вызывают строковое представление соответствующего типа: у предмета это карточка, у перемещения — маршрут и статус.

23. **Композиция.** Построение сложного объекта из связанных объектов. В широком учебном смысле Item содержит ссылки на Category, Condition и Room. По строгой UML-терминологии эти разделяемые ссылки ближе к ассоциации, поскольку справочники живут независимо.

24. **Композиция и наследование.** Композиция описывает «имеет», наследование — «является». Item имеет Room, но не является Room.

25. **Композиция в Booking.** В примере методички Booking содержит ссылки на Room и User. В моей теме аналог — Movement, связанный с Item и двумя Room; отдельного Booking нет.

26. **Декоратор.** Вызываемый объект, который принимает функцию или класс и возвращает объект для замены исходного имени; запись начинается с @.

27. **Зачем декораторы.** Добавляют поведение или изменяют способ доступа без изменения места вызова. В проекте @property обеспечивает чтение атрибутов, @classmethod создает объект из данных.

28. **Функция-обертка.** Функция, вызывающая исходную и выполняющая действия до или после нее. Пользовательская обертка в проекте не требуется.

29. ***args и **kwargs.** Принимают произвольные позиционные и именованные аргументы и позволяют передать их исходной функции в обертке.

30. **functools.wraps.** Копирует важные метаданные исходной функции на обертку, например __name__ и __doc__, и задает __wrapped__.

31. **@staticmethod.** Размещает функцию в пространстве имен класса без автоматического self или cls. В проекте такой метод не нужен: общие проверки оставлены обычными функциями.

32. **staticmethod и обычный метод.** Статический метод не получает экземпляр автоматически, обычный метод получает self и работает с его состоянием.

33. **@classmethod.** Метод получает класс cls. Item.from_dict — альтернативный способ создания объекта из JSON.

34. **classmethod и метод объекта.** classmethod работает с классом и может создавать экземпляр; обычный метод получает конкретный экземпляр и меняет его состояние.

35. **@property.** Позволяет читать результат метода как атрибут. item.total вычисляет стоимость; свойства без setter защищают от обычного прямого присваивания.

36. **Почему status без скобок.** В примере booking.status может быть свойством @property. В моей теме аналог — movement.cancelled и item.total.

37. **Сущности проекта.** Предмет Item, категория Category, состояние Condition, помещение Room и запись перемещения Movement. CuttingItem — специальный вид Item.

38. **Почему Room — класс.** Помещение имеет собственный ID и название; один и тот же объект используется предметами и журналом, что выражает общую сущность.

39. **Атрибуты Room.** Унаследованные _id и _name; публичные свойства id и name. Вместимости нет, поскольку в моей теме ее учет не предусмотрен.

40. **Операции Room.** Предоставляет ID, название и строковое представление. Проверка возможности перемещения относится к Item, а не искусственно добавляется в Room.

41. **Почему Booking хранит Room.** В примере это дает доступ к данным и методам помещения. В моей теме Movement хранит source и target как Room, чтобы связь существовала в объектной модели; в JSON остаются ID.

42. **Почему Booking связан с User.** В примере User обозначает автора бронирования. В текущей системе учета пользователей нет; добавлять их только ради копирования примера не требуется. Они запланированы для веб-версии.

43. **Какие функции стали методами.** Проверка пригодности — Item.usage_status, расчет — свойство total, перемещение — Item.move_to, смена состояния — Item.change_condition, отмена записи — Movement.cancel.

44. **Какие функции остались.** Поиск, сортировка, статистика и добавление в коллекцию остаются в inventory.py, загрузка/сохранение — в storage.py, ввод — в utils.py. Они относятся к коллекциям, файлам и интерфейсу.

45. **JSON в объекты.** load_data читает JSON; import_data проверяет структуру, создает справочники, затем Item.from_dict создает предметы. По ID предметов восстанавливаются ссылки Movement на те же экземпляры.

46. **Объекты в JSON.** export_data вызывает to_dict у предметов и перемещений. Вместо ссылок сохраняются ID. save_data пишет временный файл и заменяет основной только после успешной записи.

47. **Изменение коллекций.** В ПР2 items и moves содержат словари; в ПР3 — экземпляры Item и Movement. Справочники представлены словарями объектов. Внешний JSON-формат не изменился.

48. **Адаптация тестов.** Сохранены проверки операций через общий интерфейс функций. Добавлены проверки типов, наследования, свойств, одинаковых объектных ссылок после загрузки и совместимости с JSON ПР2.

49. **Как проверить сохранение функций.** Выполнить общие тесты ПР2 для ПР3, проверить меню, JSON и повторный запуск. В комплекте все 38 основных тестов ПР2 сохранены и добавлены 4 объектных: всего 42.

50. **Роль main.py.** Запуск, загрузка данных, числовое меню и обработка ошибок. Правила предметной области находятся в моделях и inventory.py, работа с файлом — в storage.py.
