# Кухонный учет — ПР9, ПР10, ПР11

Система учета кухонного инвентаря. Группа ЭФБО-12-24.
Предмет, категория, состояние, помещение и история перемещений.

## Первый запуск: Windows, Git Bash

Нужен Python 3.10+. Открой Git Bash в папке с manage.py:

```bash
py -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
./.venv/Scripts/python.exe manage.py migrate
./.venv/Scripts/python.exe manage.py import_legacy
./.venv/Scripts/python.exe manage.py createsuperuser
./.venv/Scripts/python.exe manage.py runserver
```

Открой http://127.0.0.1:8000/. Войди созданным аккаунтом через «Войти».
Имя и пароль выбираешь сам; готовых паролей в проекте нет.
Для Linux/macOS: `python3 -m venv .venv`, затем `./.venv/bin/python`.

**import_legacy выполняется один раз, в пустую базу.** Если база уже заполнена,
команда безопасно откажет. Не удаляй свою db.sqlite3 ради повторного импорта.
При обновлении старой версии сначала сохрани ее копию, выполни migrate.
При следующем обычном запуске достаточно:

```bash
./.venv/Scripts/python.exe manage.py runserver
```

Остановка сервера — Ctrl+C. Сохраненные изменения останутся в db.sqlite3.

## Как пользоваться

| Раздел | Что доступно |
|---|---|
| `/items/` | Каталог, поиск по названию/категории, фильтры и сортировка |
| `/items/create/` | Добавление партии, цены в копейках, фото (после входа) |
| `/items/2/`, `/items/2/edit/` | Карточка и редактирование предмета |
| `/items/available/` | Исправные предметы по помещению |
| `/rooms/`, `/rooms/<slug>/` | Помещения и их инвентарь |
| `/movements/` | Фильтры даты, статуса, помещения, предмета; поиск и страницы |
| `/movements/create/` | Новый план перемещения (после входа) |
| `/movements/<id>/` | Карточка, редактирование плана, выполнение и отмена |
| `/statistics/` | Количества, стоимость, категории, состояния и помещения |
| `/admin/` | Административная панель |

1. Добавь предмет или выбери готовую партию из восьми примеров.
2. Открой «Новое перемещение», выбери исправную партию, другое помещение и дату.
3. После сохранения появится план. Помещение пока остается прежним.
4. В назначенный день нажми «Выполнить перемещение»: помещение изменится.
5. План можно изменить или отменить. Отмена выполненной последней записи
   вернет предмет в исходное помещение; более раннюю запись сначала отменить нельзя.

На одну партию может быть один активный план в день. Прошедшая дата, неисправная
партия, одинаковые помещения и повторный план отклоняются с ошибкой в форме.
Отмененные/выполненные планы не блокируют новое планирование.
Если после планирования предмет уже переместили, отредактируй план перед выполнением.
Списанный предмет нельзя восстановить. Помещение при редактировании предмета
заблокировано: используй перемещение. Изменяющие действия требуют POST и CSRF,
входа и соответствующих прав. Гость может просматривать сайт.

## Что сделано по практикам

**ПР9.** Модели Category, Condition, Room, Item и Movement, связи ForeignKey,
PROTECT и related_name, миграции, безопасный перенос данных ПР7. Чтение сайта
переведено на ORM; фильтры, сортировка, агрегаты, annotate и Paginator работают.
Перечень более 15 разных ORM-выражений: `docs/ORM_QUERIES.md`.
CRUD с откатом: `python manage.py orm_demo`. На этапе ПР9 прошли 68 тестов.

**ПР10.** Все модели зарегистрированы в Admin: столбцы, поиск, фильтры,
сортировка, inline-история и права. TextChoices и методы QuerySet active(),
completed(), cancelled(), for_date(); миграция данных cancelled → status перед
удалением старого поля. GeneratedField вычисляет стоимость партии. Помещения
имеют английский slug и get_absolute_url(). Общие данные задает контекстный
процессор. На этапе ПР10 прошли 75 тестов.

**ПР11.** MovementFilterForm (GET), MovementForm и ItemForm (ModelForm),
создание и редактирование, ошибки полей/формы, схема POST → redirect → GET,
POST-отмена/выполнение и сообщения. Дополнительно — ImageField, request.FILES,
multipart/form-data и ограничения загрузки PNG/JPEG/WEBP (5 МБ, 4096×4096).
Фото сохраняются локально в media/. В итоговой версии прошли 97 тестов.

## Данные и миграции

Новая ORM-база db.sqlite3 создается migrate и исключена из Git. Исходная
`data/inventory.sqlite` (8 партий, 3 перемещения) остается неизменным источником
ПР7. `import_legacy` переносит ID, справочники, партии и связи одной транзакцией.
Повторный импорт в непустую базу запрещен. JSON и main.py — прежняя отдельная
консольная реализация; она не изменяет ORM-базу.

Миграции: items/0001 — сущности, items/0002 — GeneratedField и заполнение slug
до UNIQUE, items/0003 — фото; movements/0001 — история, movements/0002 —
статусы и преобразование данных. Старое cancelled=False означает COMPLETED,
True — CANCELLED: исторические перемещения уже были фактически выполнены.
Уникальный активный план и разные помещения защищены ограничениями базы.

## Проверка и Debug Toolbar

```bash
./.venv/Scripts/python.exe manage.py check
./.venv/Scripts/python.exe manage.py showmigrations
./.venv/Scripts/python.exe manage.py makemigrations --check --dry-run
./.venv/Scripts/python.exe -m pytest -q
./.venv/Scripts/python.exe -m flake8 . --extend-exclude=venv
```

Debug Toolbar устанавливается с requirements-dev.txt и включается явно:
```bash
DJANGO_DEBUG_TOOLBAR=1 ./.venv/Scripts/python.exe manage.py runserver
```
В каталоге при анонимном просмотре 5 запросов: COUNT, выборка с JOIN и три
справочника. Тесты подтверждают отсутствие N+1 для связанных объектов.
Без переменной окружения панель выключена.

Отчеты PDF и редактируемые MD лежат в reports/; реальные скриншоты браузера —
в reports/screenshots/PR10 и PR11. Текст результатов проверки — reports/checks.txt.
Короткая подготовка к защите — DEFENSE.md. Прохождение личного кабинета
Яндекс Практикума в отчетах не отмечено без подтверждения.
